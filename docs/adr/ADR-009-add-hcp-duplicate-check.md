# ADR-009: add_hcp 写前模糊查重与确认语义

## 状态
已采纳

## 背景
`add_hcp` 是对外 MCP 2.0 的写入口。调用方可能以不同 `hcp_id`、不同姓名写法（拼音、拉丁变体、1 次拼写差异）为同一医生重复建档。仅按 `hcp_id` 精确查重无法覆盖同人异档；同人双档会导致洞察与一人一策分裂，事后合并成本高。`query_hcp` 已有成熟的姓名匹配规则（中文精确；拉丁归一、词序互换、1 次编辑距离）。

## 决策
1. 写库前用与 `query_hcp` 相同的姓名匹配规则查重：`name_zh` 走中文精确，`name_en` 走拉丁档位，分别查找。
2. 命中疑似同人（编号不同的姓名命中）时不写库，返回 `status: "confirmation_required"` 与 `possible_duplicates[]`（含 `hcp_id`、姓名、医院、科室、命中档位；医院/科室归一相同者排前）。
3. 调用方带 `confirm_not_duplicate: true` 重调即写入；服务端不做二次质询。`hcp_id` 精确查重不受该参数影响，仍拒绝覆盖已有 Twin。
4. 医院/科室只做归一相等（去空格、忽略大小写），用作排序信号，不引入医院模糊规则。
5. 查重与写入落点在 `@hca/db` 共享服务 `confirmAndSaveTwin`；MCP handler 与 Web BFF 复用同一服务。BFF 是否同样启用拦截另开任务决定。

## 原因
- 漏报代价（同人双档、洞察分裂、事后合并）高于误报代价（一次确认往返）。
- 复用 `query_hcp` 既有匹配代码，查重行为与查询一致，无第二套姓名算法。
- MCP 单次调用无法中途等待人工确认；结构化状态 + 确认参数是所有客户端都可用的交互形态。

## 后果
- 同名不同院的常见中文重名会被拦下一次，由调用方/人确认放行；库内规模小，误报成本可控。
- 共享服务返回形状扩为 union：`confirmation_required` 或 `saved`；成功分支形状不变。
- 将来库规模增长、误报显著时，再评估按医院/科室豁免或分置信档，另立新决策。
