# 制药行业 HCP Personalized Engagement Assistant

- 为药企量身定做的，为 HCP (Health Care Professional) 建立数字分身，提供个性化 Engagement 的建议
- 内建 hcp-twin-mcp MCP，全网检索 HCP 的信息（个人信息、职业轨迹、科研动向、活动热力、级别标签等），生成数字分身与 HCP 洞察
- 搭建 medical-knowledge-base RAG：**按专科按需**灌注前沿学术资料 + HCP Engagement 合规文件（不做全科预灌）
- 内建 hcp-engagement-agent 智能体，根据数字分身与洞察推荐个性化 engagement 建议

# 产品包含：

## Web App「HCP Personalized Engagement Assistant」交互入口

四个 Tab（**HCP洞察 / 一人一策**仅在已打开某分身详情后显示；列表 / 新增 / 修改时隐藏，Specimen Index 为「—」）：

| Tab | 职责 |
|-----|------|
| **数字分身** | 入口为**已建分身列表**（列表本身不算选定）；新增进入**空白**录入（不预填样例 HCP）→「查询 HCP」消歧→确认保存；修改进入编辑；**打开详情**后解锁洞察/一人一策；详情含一句话洞察、级别标签、职业轨迹；可删除；详情可触发「构建情报」补齐 Stage A–E |
| **HCP洞察** | 一句话洞察、科研方向（含主要成果）、活动热力四列表、已知近期学术活动、兴趣与证据（可链） |
| **一人一策** | 方案以**选项卡**展示；页底嵌入与 Agent 的短对话 |
| **HCP Engagement Agent** | 标准对话智能体：历史上栏（cookie）、附件上传、面板可 resize |

## hcp-twin-mcp MCP

- 全网采集公开信息：职业轨迹、文献、科研动态、活动热力等
- 写入香港 Postgres 数字分身；绑定文献检索号（AuthorIds）
- **级别打标**（`hcp_tier` + `role_tags`）：按公开影响力分层，禁止处方潜力打标
- 形成洞察：在做什么、对什么感兴趣、可能想要什么

### HCP 文献查询站点（按优先级）

**准入**：公开 API · 国内可访问 · 免登录（不做爬虫）。

| 优先级 | 站点 | 网址 | 用途 |
|--------|------|------|------|
| P0 | PubMed | https://pubmed.ncbi.nlm.nih.gov/ | 生物医学主库；PMID / 作者簇 |
| P0 | ORCID | https://orcid.org/ | 作者唯一号；拉作品 |
| P0 | OpenAlex | https://openalex.org/ | 作者 / 作品图谱 API |
| P1 | Europe PMC | https://europepmc.org/ | PubMed 互补 |
| P1 | Crossref | https://www.crossref.org/ | DOI 元数据归并 |
| P2 | ClinicalTrials.gov | https://clinicaltrials.gov/ | 试验旁证 |

消歧顺序：`orcid` → PubMed 作者簇 → `openalex` → Europe PMC / Crossref。详见 [`literature-sources.md`](../knowledge/mcp-hcp-virtual-twin/literature-sources.md)；设计 [`mcp/mcp-design.md`](./mcp/mcp-design.md)。

## medical-knowledge-base RAG

- **按专科按需**学术索引（Twin specialty/themes 触发）；同专科缓存复用
- HCP Engagement 合规文件（手灌种子 + 租户 SOP）

## hcp-engagement-agent 智能体

- 根据数字分身洞察 + 学术 RAG + 合规 RAG
- 推荐个性化一人一策；支持对话迭代与附件上下文

## MVP 划分（4 个可独立闭环）

### 闭环原则（强制）

1. **一批一事**：每个 MVP 只交付一条可演示的用户/运维闭环；验收一句话必须在本批内可跑通。
2. **禁止前向依赖**：MVP-N **不得**依赖 MVP-N+1 的能力才能「看起来完成」（禁止 stub 冒充下级 MVP）。
3. **允许后向依赖**：MVP-N 可以依赖 **已验收** 的 MVP-1…N-1；上游未就绪时用 **fixture / mock**，且 fixture 路径写进本批验收标准。
4. **缺能力就移出本批**：若某 UI/文案暗示下级能力，该能力必须与触发它的管线同批交付，或从本批删除。

### 批次对照（历史 → 现行 4 批）

| 更早 | 上一版（5 批） | **现行（4 批）** | 说明 |
|------|----------------|------------------|------|
| 旧 7 批之 1–2 | MVP-1 身份 + MVP-2 情报构建 | **MVP-1** Twin 工作台 | 身份 CRUD 与 `build_twin`/真进度 **同批**；产品路径 live |
| 旧 7 批之 3 | MVP-3 | **MVP-2** HCP 洞察工作台 | 洞察八块；可用 fixture Insights |
| 旧 7 批之 4–5 | MVP-4 | **MVP-3** 知识库 | 合规底座 + 学术按需 |
| 旧 7 批之 6–7 | MVP-5 | **MVP-4** Engagement | 一人一策 + open_chat |

建议实现顺序：**MVP-1 → 2**；**MVP-3 可与 2 并行**；**MVP-4 在 2+3 之后**（Insights fixture + 合规 retrieve 即可验收）。

| MVP | 名称 | 独立闭环（验收一句话） | 主覆盖功能 | 依赖 |
|-----|------|------------------------|------------|------|
| **MVP-1** | Twin 工作台（身份 + 情报） | 空白录入→查询消歧→确认保存→列表/详情/改/删；详情触发 `build_twin`→进度可查→Stage A–E 落库→详情可见职业/科研/热力/Insights 草稿；浏览器只调 BFF；产品 `TWIN_MODE=live` | F-WEB-001–016、035–036、040；F-MCP-001–035 | `domain` + `db` + live MCP |
| **MVP-2** | HCP 洞察工作台 | 洞察 Tab 八块可读可链；`synthesizeDoingNow` 与分身同源；**验收允许 fixture Insights**（不要求本批现场重跑 Stage） | F-WEB-017–025、037、041；F-AGT-001、001a–d、005、008–010、028 | 已验收的 MVP-1；或 Insights fixture |
| **MVP-3** | 知识库（合规 + 学术按需） | 手灌合规种子 → `retrieve_compliance` 命中含 `clause_id`；专科 on-demand → `retrieve_academic` 可过滤命中；可选 F-WEB-039 触发可观测 | F-RAG-001–027（含 002a–d）；F-WEB-039 | Qdrant + corpus；可与 MVP-2 并行 |
| **MVP-4** | Engagement（一人一策 + Agent） | 生成 3–5 方案（双引用）→ 合规闸门 → `revise_options`；`open_chat` 多轮 + 历史/附件/resize | F-WEB-026–034、038、042–043；F-AGT-002–007、011–027、019、022–023、029–030；F-RAG-021–022、025 | **已验收的 MVP-2 + MVP-3**（学术可 sparse） |

### 本批明确不做（防假闭环）

| MVP | 本批禁止出现 |
|-----|----------------|
| MVP-1 | 确认保存后用 stub 假装构建已完成；产品默认 mock fixture 冒充 live 消歧/构建 |
| MVP-2 | 要求 live 爬完才出洞察；合规检索 / Options |
| MVP-3 | 一人一策生成；开放对话 |
| MVP-4 | 正式 MLR 电子签、CRM 回写 |
